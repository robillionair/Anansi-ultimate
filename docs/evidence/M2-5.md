# M2.5 — Snapshot and restore preview evidence

Status: implementation candidate; final native/browser acceptance, full regression and CI are in progress. This record supersedes the early directory-copy-only checkpoints. No M2 completion claim.

## Remaining implementation acceptance (defined before continuation)

Snapshot assembly must capture a coherent SQLite read snapshot plus exactly its immutable bodies, preserve complete record/relationship revisions and settings, and exclude other workspaces from workspace scope. Managed backup artifacts use durable job leases and are visible only after verified publication. A distinct application scope covers the application catalog and referenced bodies/artifacts. Scheduling defaults off, requires explicit plaintext/destination/retention consent, retains snapshots without pruning, runs only while a host process is open, and reports missed intervals. Restore verifies schema, member paths, sizes, hashes, ownership and foreign keys before creating a fresh workspace; all internal IDs are mapped and original identities remain recorded. Existing roots and source archives stay unchanged. Both adapters must use generated contracts, owned IDs and the same core policy. Browser/native workflows must actually exercise preview, restore, failure and restart behavior. No vault or crypto implementation belongs to this task.

Implemented in this increment:

- Versioned `anansi-workspace-backup` manifest with bounded size and strict fields.
- Safe relative member paths with link, traversal, duplicate and overwrite rejection.
- SHA-256 member verification before preview and before restore publication.
- Fresh-target materialization that preserves the source package and refuses a non-empty target.

Executed validation:

- `node scripts/cargo.mjs fmt --all`
- `node scripts/cargo.mjs test --locked -p anansi-core --test backup_restore` — 2 passed.
- Existing core unit tests compiled successfully while the broader suite was running; the full M2.5 acceptance suite is not yet claimed.
