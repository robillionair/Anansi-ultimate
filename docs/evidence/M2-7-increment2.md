## Implemented boundary

- Root admission and one KDF permit per configured private host/user namespace use OS file locks. Contention fails immediately; files are never unlinked and no PID/age-based lock stealing occurs. All trusted instances must choose the same namespace. This is not a system-wide permit across unrelated OS users. Public primitive helpers remain low-level; application integration must call the admitted store API rather than invent an alternate derivation path.
- Explicit `VaultStore` schema-9 cutover requires a verified owned M2.5 workspace backup with identical complete source fingerprint, recovery acknowledgement and consent to retain plaintext originals. A SQLite immediate transaction switches schema, active generation, opaque membership/inventory and durable epoch only after synced encrypted files are authenticated on read-back. Ordinary application `Core` remains schema 8 and refuses schema 9; stale plaintext SQL writers hit schema-9 triggers. No live root is upgraded automatically.
- Typed authenticated payloads contain complete metadata, title, tags, timestamps, provenance, original privacy, bodies, every record revision and every relationship revision. Schema 8 has no tags field: migration records an empty tag list, rather than claiming to import nonexistent tags. Future typed payload tags round-trip. Graph projections and contiguous revision/current-pointer maps are checked. Nested duplicate JSON keys, unknown fields, invalid source fields, inconsistent histories and resource excess are rejected. Plaintext canonical SQL rows for the selected workspace are removed only by committed explicit cutover.
- Opaque random ciphertext filenames and an encrypted generation manifest avoid exposing per-record history/graph in the new SQL inventory. The index necessarily exposes workspace/vault/generation/record identifiers, wrapped slots, epochs, coarse file counts/lengths and ciphertext hashes. This is not metadata-free storage. Legacy body files, old database/WAL/free-page remnants, verified M2.5 plaintext backups and failed staging are deliberately retained; this core increment does not certify forensic erasure or complete at-rest conversion of those prior copies. No product activation may imply otherwise.
- Every store read/export rechecks caller/root/context and durable epoch under the root lock. Explicit lock, rotation and rollback advance the epoch. Full rotation creates a new independent DEK/recovery key, encrypts all histories/graph anew and commits a new generation; old generations and slots remain for explicit recovery. No claim that old independent backups become undecryptable. Before commit old state is authoritative; after commit new state is authoritative, including an error from a post-commit observer. Authenticated rollback is a separate epoch-advancing transaction. Retained journals are never automatically executed at startup.
- Recovery keys use strict RFC4648 uppercase unpadded Base32 (52 characters grouped 7/7/7/7/6/6/6/6). Display is offered once per pending setup. The private receipt requires display, explicit saved-copy consent, a matching random challenge and actual supplied-key authenticated recovery-slot unwrap. No serializable receipt or renderer secret entry is introduced.
- `ANCB` v1 ciphertext backups copy only catalog-owned opaque ciphertext files and wrapped source slots; locked previews explicitly report `authenticated=false`. `ANSV` encrypted exports require a valid session and separate export passphrase, rewrapping the copied source slot without altering the source. Fresh restore authenticates every source member/context before staging, remaps internal record/revision/graph IDs, re-encrypts under fresh destination keys and preserves origin mappings and pre-existing destination workspaces. Neither format runs software or accepts filesystem member paths.
- File reads require private owner/protected-DACL verification and reject links/reparse points. New ciphertext is create-new and synced. Batched Windows permission checks execute the unchanged existing `protect.ps1` policy for each file in one hidden process; only filesystem paths/modes enter that subprocess. No secret keys or payloads are command arguments or environment values. Unix checks retain owner-only permissions. This tests process-crash recovery, not sudden power-loss/filesystem hardware certification.
