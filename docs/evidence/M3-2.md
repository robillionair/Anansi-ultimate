Status: pre-implementation design and acceptance specification. Acceptance defined in [the detailed plan](../../plans/03-search-and-ollama.md) before code. User explicitly authorized continuing Milestone 3 while waiting for upstream audit feedback; Milestone 2 remains incomplete and untouched. Pure Rust, p=4 and the G1 audit gate remain unchanged.

Acceptance scope: rebuildable full-body indexing, current-pointer synchronization, metadata and entity filtering, deduplication, recency handling, grounded evidence locations (Markdown heading and line), privacy boundary excluding Sealed records from plaintext indexes, and an automated retrieval evaluation benchmark suite covering paraphrases, contradictions, temporal facts, and missing evidence.

## Architectural design and privacy boundaries

1. **Rebuildable Index Architecture**:
   - Canonical user knowledge resides in immutable UTF-8 Markdown files at `content/{workspace}/{record}/{revision}.md` and SQLite metadata table `memories`.
   - The body search index is an SQLite FTS5 table designed to be completely rebuildable on demand from canonical files and metadata.
   - If the index table is missing, damaged, or requires synchronization, a rebuild operation scans all current active revisions in the workspace, validates SHA-256 body hashes, and repopulates the index.
   - Index rebuild does not discard, overwrite, or mutate canonical metadata or content files.

2. **Privacy Boundary and Vault Isolation**:
   - Master Spec §75 and AN-031 require an audited vault for Sealed records. M2.6/G1 remains open pending independent audit evidence.
   - **Crucial security invariant**: Sealed memories MUST NEVER be inserted into any plaintext SQLite FTS5 index.
   - Index population queries strictly enforce `WHERE privacy != 'sealed'`.
   - Private and Standard records are stored locally with restrictive OS-level permissions.
   - Full-body search queries never inspect, match, or leak terms from Sealed records.

3. **Current-Pointer Synchronization**:
   - Only current revisions (referenced by `memories.current_revision`) are active in the body index.
   - When a memory is revised, superseded, or restored, the index synchronization updates the record's indexed content so only the new current revision is returned.
   - Historical revisions remain accessible via the historical revision reader (`memory_command("read")`) but do not pollute current search queries.

4. **Query Syntax and Sanitization**:
   - Queries support multi-word search (AND-joined by default), exact phrases in double quotes (`"exact phrase"`), and prefix wildcards (`term*`).
   - Query input is bounded to 512 UTF-8 bytes and at most 16 terms.
   - FTS5 syntax characters (such as `:`, `^`, `NEAR`, `{}`) are sanitized or escaped to prevent SQL injection or FTS5 syntax errors.
   - Empty, whitespace-only, or punctuation-only queries return an actionable `ErrorCode::InvalidSearch` error.

5. **Entity, Metadata, and Lifecycle Filtering**:
   - Search accepts optional filters:
     - `kind`: filter by knowledge kind (`memory`, `note`, `project`, `task`, `person`, `organization`, `decision`, `event`, `document`).
     - `projectId`: filter by project membership.
     - `status`: filter by lifecycle status (`Proposed`, `Confirmed`, `Temporary`, `Durable`, `Superseded`, `Archived`).
     - `includeArchived`: boolean (default `false`).
     - `includeExpired`: boolean (default `false`).
   - Filter predicates are evaluated in conjunction with the FTS5 text match.

6. **Grounded Evidence Locations and Snippets**:
   - For each matching record, the retrieval engine extracts:
     - A highlighted snippet containing query terms with surrounding context.
     - The enclosing Markdown section heading (`# Heading 1`, `## Heading 2`, etc.) where the match occurred.
     - The approximate line number in the source Markdown body.
   - Enables grounded citations for the upcoming Context Compiler (AN-010) and Ask ANANSI (AN-006).

7. **Deduplication and Recency Weighting**:
   - Deduplication: identifies records with identical body content (matching SHA-256 hash) or near-identical snippets, grouping or flagging duplicates to prevent redundant context.
   - Recency weighting: computes a composite ranking score blending lexical BM25 relevance with temporal decay based on `updated_at` and `event_date`.
   - Recent records and records with matching event dates rank higher for temporally sensitive queries.

## Retrieval evaluation benchmark suite

Master Spec §11 and §78 require a benchmark suite for:
- **Paraphrases**: evaluates lexical matching behavior against alternative vocabulary and synonyms, documenting baseline lexical limitations to be augmented by M4 semantic embeddings.
- **Contradictions**: tests corpora containing conflicting facts across revisions or records, verifying that recency weighting and supersession correctly prioritize current truth.
- **Temporal facts**: tests queries with chronological constraints (`event_date`, validity periods `valid_from` / `valid_until`), verifying time-aware filtering.
- **Missing evidence**: tests negative queries where query terms are completely absent from the corpus, verifying zero false positive hallucinations and truthful empty results.
- **Citation accuracy**: tests that returned section headings and line numbers match the exact location in the synthetic test documents.

## Performance bounds and corpus limits

- Up to 10,000 active records per workspace.
- Up to 256 KiB body size per record (`content::MAX_BODY`).
- Total indexed corpus tested at 1,000 and 10,000 records.
- Paginated results with `limit` (1..100) and `next_offset`.
- Rebuild operation bounded by transaction time and memory limits without blocking UI.

## Acceptance criteria — defined before coding

1. Core full-body search function `body_search` searches both titles and Markdown bodies across all nine knowledge kinds.
2. Rebuild function `rebuild_search_index` reconstructs the FTS5 index from canonical Markdown files and SQLite metadata.
3. Sealed memories are strictly excluded from the FTS5 index table; no sealed text or metadata is searchable.
4. When a memory is revised, searching for terms unique to the old revision returns no matches, while terms unique to the new revision match.
5. Exact phrase search (`"..."`) matches exact word sequences only.
6. Prefix search (`...*`) matches words starting with the prefix.
7. Metadata filters (`kind`, `projectId`, `includeArchived`, `includeExpired`) correctly restrict full-body results.
8. Search results return snippet, enclosing Markdown section heading, and line number.
9. Deduplication correctly detects identical body hashes across distinct records.
10. Recency scoring ranks newer/closer event-date records above older records with identical lexical match.
11. Retrieval evaluation suite passes all benchmark tests (paraphrase baseline, contradiction resolution, temporal facts, missing evidence).
12. Shared UI Search component updated to support full-body search toggle, snippet/section display, and filter controls.
13. Existing title search, memory CRUD, entities, export, and backup tests remain 100% green.
14. Both desktop and browser verifiers pass with zero unexpected external network calls.
