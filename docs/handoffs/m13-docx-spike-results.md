### 2.1 Findings

1. **The zip crate enforces the declared size during
   inflation.** `zip` 9.5's `Crc32Reader` carries the
   declared uncompressed size as a read-time limit
   (`src/crc32.rs`: errors the moment `bytes_read`
   exceeds the limit). A lying declared size is refused
   after ~1,000 bytes decompressed, by the crate itself,
   whether or not the spike's cap is active. The 16 MiB
   capped reader is therefore the second layer, not the
   first (§4.1, correction 2). The bound holds either
   way; the layer that fires depends on which check can
   see the lie.
2. **The encrypted check needs metadata-only entry
   access.** The first spike implementation walked the
   archive with `by_index` (open-for-read), which errors
   with `Password required to decrypt file` before
   `encrypted()` is reached — the refusal was correct
   but the reason was a generic parse error. The walk
   now uses `by_index_data` (central-directory metadata
   only) for the encrypted/name/size checks and opens
   only `word/document.xml` (correction 3).
3. **A section `heading` is the plain heading text.**
   The first spike run stored the rendered body line
   (`"# Harbor Ledger"`) as the section heading; the
   manifest (generator) stores the plain text. The
   prefix is body formatting, not the heading: the
   provenance record (`DocxSectionProvenance.heading`)
   stores the plain text. Corrected in the spike; the
   manifest was already right (correction 1).
   **Not changed by this:** what Ask/search *display*.
   The citation's section heading comes from the body
   line via `context.rs` chunking, which stores the
   `#` line verbatim (existing Markdown behaviour —
   its test asserts `Some("# Guide")`) and the Ask UI
   renders it verbatim, so a DOCX citation reads
   `document · # Harbor Ledger (line N)`. The
   provenance heading and the displayed heading are
   two different fields; only the provenance one is
   plain.
4. **`outlineLvl` is reliable — proven, not dropped.**
   The first fixture set had no paragraph exercising
   the fallback: every heading (including the
   LibreOffice one) used `w:pStyle`. Added
   `outline-lvl.docx`: all four headings carry only
   `w:outlineLvl` (0/0/1/2), no `w:pStyle` — output
   identical to normal.docx (297 chars, 16 lines,
   4 sections). The fallback stays. `outlineLvl` ≥ 3
   is ignored (paragraph stays plain) — the spike only
   accepts 0–2 (correction 4).
5. **Field codes and track changes behave exactly as
   designed.** field-codes extracts `Annex link`, `3`,
   `After the fields.` — the HYPERLINK and PAGEREF
   *results* are included, the `w:instrText` codes
   themselves are absent. track-changes extracts
   `Inserted text. Kept text.` / `Final text.` —
   `w:ins` included, `w:del` (both `w:delText` and
   `w:t` inside `w:del`) skipped.
6. **External content is never fetched and never
   recorded.** external-hyperlink extracts `External
   annex link` / `Plain paragraph after the link.` —
   display text only; the `https://example.invalid/…`
   URL appears nowhere in the body. The spike opens no
   network path at all: only `word/document.xml` is
   read, and `TargetMode="External"` relationships are
   ignored entirely.
7. **No form feed anywhere.** The page-break paragraph
   in normal.docx yields two lines (`Before the break`
   / `After the break`); no `\x0c` appears in any
   extracted body (verified by the manifest-exact body
   match on every imported fixture). The PDF
   page-chunking branch in `context.rs` can never be
   triggered by a DOCX body.
8. **The `<!DOCTYPE` pre-scan was un-fixtured until
   this run.** The §7 fixture list did not include a
   DOCTYPE case, so the security rule had code but no
   evidence. Added `doctype.docx` (a DOCTYPE with an
   entity declaration inside `word/document.xml`):
   refused by the pre-scan before any XML parsing.
9. **List numbering is the one deliberate divergence
   from LibreOffice.** §5: LO's txt export expands
   list bullets (`    - First item`); the spike gives
   plain paragraphs (`First item`), per design §4
   (recorded known limit, not a defect).

## 3. Bomb: peak memory and elapsed time

Per-process runs (one fixture per process; peak is Linux
VmHWM). `/usr/bin/time` is not installed on this VM, so
elapsed + peak come from the spike's own per-process
`ELAPSED_MS` / `PEAK_RSS_KB` (the same method as the PDF
spike's per-process runs).

| Case | Result | Elapsed | Peak RSS |
|---|---|---|---|
| Committed bomb (56,110 raw bytes; `word/document.xml` inflates to ~20 MB; declared size patched to 1000), capped | REFUSED — crate's declared-size check | **0 ms** | **3,992 KB** |
| Committed bomb, uncapped | REFUSED — same crate error | **0 ms** | **4,056 KB** |
| Honest 20 MB bomb (20,957 raw bytes; declared size 20 MiB), capped | REFUSED — `single entry exceeds 8 MiB` (declared-size pre-check) | **0 ms** | **5,464 KB** |
| Honest 20 MB bomb, uncapped | read all 20,971,520 chars, then REFUSED — text cap | **901 ms** | **30,164 KB** |
| Worst bomb (1 GiB expansion, in-memory synthetic: 1,043,497-byte raw, declared size 1000), capped | REFUSED — crate's declared-size check | **0 ms** | see note |

- The committed bomb is refused identically capped and
  uncapped because the crate's size check fires first
  (§2.1.1). The honest-size comparison is the one that
  shows the cap's value: capped 0 ms / ~5 MB vs
  uncapped 901 ms / ~30 MB (full 20 MB inflated, then
  the text cap trips).
- The 1 GiB variant's peak is not reported as a
  per-variant number: it runs in the `worstbomb`
  process, where VmHWM (process-wide high-water mark)
  is dominated by the CappedReader unit check's 37 MB
  allocation (20 MB source + 16.7 MB sink). Its
  elapsed time (0 ms) is the meaningful number; the
  honest-process peaks above are the clean comparison.
- **CappedReader unit check** (in `worstbomb` mode,
  direct proof the mechanism works): a synthetic 20 MB
  source through a 16 MiB `CappedReader` reads exactly
  16,777,216 bytes, then errors `expansion budget
  exceeded`. The generator streams the bomb's `A` run
  through the deflater, so bomb construction itself
  never holds the inflated form (the 1 GiB variant
  would otherwise allocate 1 GiB before the
  measurement starts).
- Every in-cap fixture extracts in ≤ 2 ms.

`libreoffice-realworld.docx` is a LibreOffice round-trip
(`soffice --headless --convert-to docx`) of normal.docx.

- Spike output for the LO fixture is **byte-identical**
  to spike output for normal.docx (same 297-char body,
  same 4 sections). The round-trip preserved everything
  the spike extracts, including heading styles, the
  table, the hyperlink, and the page break.
- Spike body vs `soffice --headless --convert-to txt`
  output of the same file: the only differences are
  the two designed behaviors — heading `# ` prefixes
  (spike) vs plain text (LO txt), and unexpanded list
  items (spike: `First item`) vs LO's expanded bullets
  (`    - First item`). Table cells, paragraph order,
  hyperlink display text, and the page break agree
  exactly (16 lines each, no form feed, no trailing
  blank lines).
- The LO fixture's document.xml uses `w:pStyle`
  headings (3 Heading + 1 Title, 0 `outlineLvl`) —
  which is why the `outlineLvl` fallback needed its own
  fixture (§2.1.4).

## 6. Design corrections (amendments to the design doc)

The design doc (`docs/handoffs/m13-docx-ingestion-design.md`)
is amended in a new §10; the corrections are:

1. **Section `heading` is plain text (§5).**
   `DocxSectionProvenance.heading` stores the heading
   text without the `# ` prefix. The prefix is body
   formatting, rendered only when joining the body and
   the section text. The spike's `sections_for` now
   keeps lines as (plain text, level) and renders the
   prefix at join time. **Display is separate:** the
   Ask/search citation heading comes from the body
   line via `context.rs` chunking (which stores the
   `#` line verbatim, as for Markdown), so citations
   read `document · # <Heading> (line N)`. The
   design's AC-D1 shorthand `<Heading>` means the
   heading text; the rendered form keeps the `#`,
   consistent with Markdown documents.
2. **Lying declared size is refused by the zip crate
   itself (§3, AC-D5).** The 16 MiB capped reader is
   the second layer, not the first: honest declared
   sizes hit the 8 MiB pre-check; lying declared sizes
   hit the crate's read-time size check (finding 1);
   the capped reader covers entries whose declared size
   the pre-check cannot trust (e.g. data-descriptor
   entries with unknown central-directory size) and is
   proven directly by its unit check (§3). AC-D5 is
   amended to: "refused during inflation at the earliest
   applicable layer, fast and low-memory" — the 16 MiB
   budget is unchanged, but the bomb no longer proves
   the capped reader fires; the unit check proves the
   mechanism.
3. **Archive walk uses metadata-only entry access
   (§4, §6).** The walk must use `by_index_data`
   (central-directory metadata only) for the
   encrypted/name/size checks; `by_index` opens the
   entry and errors on encrypted entries before
   `encrypted()` is reached (finding 2). Only
   `word/document.xml` is opened, after the walk.
4. **`outlineLvl` fallback is reliable (§4).** Proven
   by `outline-lvl.docx` (finding 4); the fallback
   stays. `outlineLvl` ≥ 3 is ignored (paragraph stays
   plain). The §7 fixture list gains `outline-lvl.docx`
   and `doctype.docx` (finding 8).
5. **Audit finding (§1).** `libsqlite3-sys` 0.38.2,
   RUSTSEC-2026-0459, is pre-existing (via rusqlite),
   medium severity, fix ≥0.39.0 — out of scope, flagged
   for the owner. No new warnings from zip/quick-xml.

## 8. What the spike does not do

- No production code: the harness is an example binary
  on this branch. The `Cargo.toml`/`Cargo.lock` changes
  on this branch are spike evidence (the exact resolved
  versions); integration re-applies the dependency
  additions on Antigravity's accepted commit.
- No Windows run: the spike ran on this Linux VM only.
  The pure-Rust dependency graph (no system libs, no
  subprocess) is the Windows-compatibility evidence;
  the Windows rerun of the ingestion suite is still
  the gate for integration.
- No data-descriptor bomb fixture: the capped reader's
  untrusted-size path is proven by its unit check only
  (§3), not by a committed fixture. A data-descriptor
  (bit 3) bomb fixture is follow-up work for
  integration if the owner wants it.
- No fixtures for `w:sdt`, `w:smartTag`, `w:tab`,
  `xml:space="preserve"`, or `w:drawing`/`w:pict`/
  `w:object` skipping: the code handles them (sdt/
  smartTag as transparent containers, like the
  fixtured `w:hyperlink`; drawing/pict/object via a
  depth counter), but no committed fixture exercises
  them. Integration tests should add them.
- The worst-case bomb (1 GiB) is an in-memory
  synthetic, not a committed fixture. The committed
  23 fixtures are unchanged by the spike run (all SHAs
  re-verified against the manifest after regeneration).
